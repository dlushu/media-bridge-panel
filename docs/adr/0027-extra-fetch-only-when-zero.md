# ADR-0027 补打只在"一条能用的都没有"时触发（取代 0005 的触发与停止口径）

- 状态：已采纳（**局部取代 [0005](0005-continuation-fetch.md)** 的触发条件、停止条件与上限口径）
- 相关：[agg/service.js](../../server/modules/agg/service.js) · [agg/settings.js](../../server/modules/agg/settings.js) · [0005](0005-continuation-fetch.md) · [0025](0025-line-filter-in-usable-judgement.md)

## 背景

0005 定的口径是"没凑够 N 条能用的就继续往下打，凑够 N 条停"。实测暴露三个问题：

1. **目标从"有版本"变成了"凑够 N 个版本"**：前面已经拿到 5 条能用的（`过滤后能用 5/8`），还要往下打
   8 条去凑第 6~8 条 —— 每一条都是一次 10 秒级的站源 `/detail`，换来的只是"版本列表多几行"。
2. **上限口径与文案不一致**：实现按"合计 ≤ N + K"封顶，而设置项与文档写的是"最多再试 K 条"。
   实测一轮日志写着 `往下打了 10 条（上限 8）`：阶段一只打了 6 条（命中不足 N），
   省下的 2 条额度被补打吃掉了，读起来像自相矛盾。
3. **单轮成本不可预期**：并发批（批宽 = N）一次发 8 条，其中往往只有一两条是必要的。

## 决定

1. **触发条件收成"零版本"**：只有阶段一**一条能用的都没有**（过滤后客户端的版本列表会是 0）时才补打；
   前面已经拿到 1 条及以上 → 一条都不补打。
2. **停止条件收成"拿到就停"**：补打仍**整批并发**（批宽 = N，沿用 0005 的并发取舍），
   **第一批拿到能用的就不再发第二批**；批内已经打回来的结果**全部落账**
   （请求已经发出去了，不列出来等于白烧）。
3. **上限改成字面口径**："最多再试 K 条" = `阶段一实际打过的条数 + K`（不再是 `N + K`）。
4. `matchExtraAll`（"匹配到底"）跟着改成：**不看 K，打到拿到一条或名单打完**。

## 理由

- **补打是兜底，不是凑数**：客户端 0 个版本是功能缺失，1 个版本已经能播；为"多几个版本"再烧几发
  10 秒级请求不划算。
- **代价与收益不对称**：实测补打的命中率很低（一轮打 8~10 条只救回 0~1 条），而成本是确定的。
- **口径要能被复述**：设置项写"最多再试 K 条"，实现就该是这么多 —— 否则页面上的数字、日志里的数字
  与实际行为三处对不上。
- **不放弃并发**：串行（批宽 = 1）能让"拿到即停"完全精确，但最坏耗时变成 K 条相加（K = 8 时约 80 秒），
  那正是当初并发化要避开的情形；因此接受"批内多打的那几条白烧"，只在批与批之间收敛。

## 备选方案

- **保持"凑够 N 条"、只改文案**：省上游的收益拿不到 —— 前面 5/8 时仍会再打 8 条，否决。
- **串行补打（批宽 = 1）**：最省上游、收敛最精确，但最坏耗时线性增长，否决（理由见上）。
- **把批宽做成 1 与 N 之间的可调值**：多一个旋钮、收益不确定，否决（要调就调 K）。
- **只打"低于分数线"的那批候选**：候选池大幅缩小，但实测真正能用的条目常常在"过线但超上限"那批里，否决。

## 后果

- **绝大多数轮次不再补打**（前面只要有 1 条能用的）：上游请求明显减少，单轮耗时不再有"最贵的那一段"。
- **零版本那轮的成本上限更清晰**：一批 `min(N, K)` 条并发，总计不超过 K 条；
  最坏耗时约为 `⌈K / N⌉ × 取详情超时`。
- **客户端版本数会更早停在"阶段一拿到的条数"**：前面只有 1 条时不再去凑更多 —— 这是本决策的意图。
- 日志随之改成：`agg 接续补打：阶段一 N 条里能用 0 条 → 往下打了 X 条（上限 K 条），拿到 Y 条能用的`，
  不再出现"上限 8 却打了 10 条"那种矛盾。
- **候选池不变**：仍取自 `ranked`（过了名字硬闸门、按分数降序、**不受分数线限制**），
  这一点 0005 与 0025 的取舍继续有效。
- 0005 的其余取舍（"可用"的判据、计数按条目、`matchExtraAll` 开关、诊断字段）**继续有效**。
