# ADR-0019 自身更新：应用代码装在数据卷，按 Release 资产安装，靠进程重启生效

- 状态：已采纳
- 相关：[update.js](../../server/modules/panel/update.js)（面板侧的安装与重启） ·
  容器引导脚本 `docker/entrypoint.js`（由维护者维护，与容器定义一起放在版本库之外） ·
  [0015](0015-source-bundle-integrity.md)（源包的信任边界） · [0006](0006-redirect-for-playback.md)

## 背景

早期镜像自包含：应用源码在构建时 `COPY` 进镜像，更新方式是换 tag、`docker pull`、重建容器。
这在"改代码的机器"上很方便，但典型部署是路由器或 NAS 上的一个容器 ——
更新意味着要到宿主机执行操作，日常使用中不便。

另一方面，本项目对**源包**已经有一套成熟做法：下载 → 校验 md5 → 运行 → 按需重启。
把同一套思路用于面板自身，机制与心智模型一致，不需要引入新的概念。

## 决定

**应用代码不进镜像**，而是安装在数据卷里；镜像只提供运行时（Node）与一段引导/监督者。

### 目录与安装

- 代码安装根：`<DATA_DIR>/app`（镜像内即 `/data/app`）。
- 每个版本一个目录：`app/<版本>/`，内含 `server.js`、`server/`、`public/`、`package.json`、`README.md`。
- 当前版本记录在 `app/current.json`（`{ version, installedAt, source }`），使用普通文件而非符号链接：
  部分卷与文件系统对链接支持不一致，且读一个文件比解析链接更直接。
- 安装流程：解包到 `app/.staging-<版本>-<pid>/` → 校验必需文件 → 原子改名为 `app/<版本>/` →
  以"临时文件 + rename"写入 `current.json`。任一环节失败都清理暂存目录并保留原有版本。

### 取得代码

- 容器启动时：若没有任何已安装版本，自动取得一次。`APP_VERSION` 指定版本，未指定则取最新 Release。
- 取得失败（网络不可达、校验不通过等）时**退出并打印排障指引**，不做静默降级。
- 只接受**正式 Release 的资产**：`media-bridge-panel-<版本>.tar.gz` 与其 `.sha256`；
  **不接受分支或任意 commit** —— 那些内容随时在变、可能是半成品，且不可复现。
- 下载地址可配置（`APP_REPO` / `APP_SOURCE_URL` / `APP_CHECKSUM_URL`），因为 GitHub 在部分网络环境下
  可达性差。除 HTTP(S) 外也接受本地路径，便于离线与内网部署。
- **sha256 必须校验**，与源包的口径一致（见 [ADR-0015](0015-source-bundle-integrity.md)）。

### 更新与生效

- 更新**只由用户手动触发**（面板「版本与更新」），不做按间隔的自动更新：
  自动更新会在用户不知情时重启面板，而面板一旦异常影响的是全部功能，与源包（影响几路）不同。
- 面板执行：下载 → 校验 sha256 → 解包 → 检查必需文件 → 安装 → 写 `app/.restart` → 进程退出。
- **生效方式是重启进程，不是重启容器**：容器 PID 1 是一段监督者循环，子进程退出后读 `.restart`，
  删除标记并拉起 `current.json` 指向的新版本。
- 非请求退出（崩溃）同样重启，起自愈作用；但 60 秒内连续 5 次即放弃并退出，避免刷屏。
- 面板在**非托管模式**下（直接跑源码，或镜像内的代码未经监督者启动）如实拒绝自更新并说明原因。

## 理由

| 做法 | 需要什么 | 风险 |
|---|---|---|
| **重启进程**（本决定） | 无 | 低。容器不停，仅应用进程在数秒内重启 |
| 退出容器，靠宿主 restart 策略拉起 | 启动时必须带 `--restart` | 中。用户遗漏该参数时会"更新后容器不再启动"；被手动停止过的容器也不会自动起 |
| 挂载 `docker.sock` 后重启容器 | 宿主机 Docker 控制权 | 高。等同于把宿主机交给面板进程，面板被攻破即宿主机被攻破 |

此外，"应用代码装在数据卷"使**发布新版本不再需要重建镜像**：只有引导与监督者逻辑变化时才需要重推镜像。

## 备选方案

- **镜像自包含，面板只提示有新版本**：可靠性最高（镜像更新是原子的），但每次更新都需要宿主机操作，
  与本项目的部署形态不匹配。
- **镜像里同时内置一份代码作为兜底**：首启不依赖网络，代价是镜像重新变大，且"运行的是内置那份还是
  数据卷那份"需要一个额外的判定规则，容易产生"更新了但没生效"的困惑。
- **直接使用分支内容**：不可复现，已排除。

## 后果

- **版本与镜像 tag 解耦**：镜像 tag 只标识运行时与引导逻辑，`/api/meta`、`/api/panel/info` 与面板界面
  才是"当前运行的是哪一版"的权威。
- `<DATA_DIR>/app` 不进入配置备份（它可以从 Release 重新取得），备份仍只覆盖设置与源清单。
- 首个版本与后续更新都依赖对外网络；因此下载地址必须可配置，且失败信息要能指明"是网络问题、怎么换地址"。
- 引导与监督者需要与安装约定保持一致（目录布局、标记文件、必需文件清单），两者一同演进。
