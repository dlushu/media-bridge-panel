# ADR-0025 线路过滤参与"这条详情对客户端有没有用"的判据（并进快照 key）

- 状态：已采纳
- 相关：[agg/service.js](../../server/modules/agg/service.js) · [agg/api.js](../../server/modules/agg/api.js) · [emby/service.js](../../server/modules/emby/service.js) · [0020](0020-detail-snapshot.md) · [0005](0005-continuation-fetch.md) · [0008](0008-no-fabricated-data.md)

## 背景

实测症状（emby 层日志 + 聚合层日志对着看）：

```
✔ agg 详情已存快照（3 站；⚠️ 但不完整：2 个源没搜到（玩偶|4K / 虎斑|4K），3 条详情没取到）
· agg 详情走快照「斗破苍穹」→ 3 站（没打源站；当初算它花了 18508ms）
✔ emby 条目详情 …「斗破苍穹」→ 1 站命中（nodejs_muou） 0 线路，1 条目定位到 S5E210
   线路过滤(/夸克原画/)：源里 4 条 → 过滤后 0 条（规则把线路全滤掉了）
```

某个站（木偶）**命中、详情也取到了**（4 条线路、定位到 S5E210），但**线路过滤规则
`/夸克原画/` 把这 4 条全滤掉了** → 客户端拿到 0 个版本。而聚合层按 ADR-0020 的判据
（"有站拿到详情就存"）把这份详情存成了快照 —— 于是在有效期内（默认 60 分钟）客户端
反复点开都是 0 版本，而且**不再尝试源站**（日志里连着四行"走快照"）。

根因是**判据的位置不一致**：过滤规则只在 emby 层拼版本列表时生效，聚合层不知道
"客户端要的是哪些线路"，于是：

- 它把"过滤后一条都列不出来"的条目**也算成"能用"** → 接续补打就此收手，不再去找别的条目/站点；
- 这份"对客户端没有用"的结果照样满足"可存快照"的判据 → 被锁定一个有效期。

## 决定

1. 线路过滤的**实现在 `agg/service.js`（只此一处）**：`lineFilter()` 产出 `{raw, re, invalid}`；
   emby 层经 `agg/api.js` 转发（`emby/service.js` 一行），聚合层判断"能不能用"时用同一个正则。
2. **"能用"的判据 = 有线路 + 过了线路过滤 + 有可播目标**（剧集定位到这一集 / 电影有播放项）——
   即 `lineVisible()` / `detailUsable(d, need, re)`，统计在 `stats.usable`。
   这就是"客户端真能列出至少一条版本"。
3. **接续补打按"能用"凑数**：过滤后为 0 的条目不算数，继续往下打（ADR-0005 的 N 条口径不变）。
4. **快照可存性从 `detailOk > 0` 收紧成 `usable > 0`**（ADR-0020 的那一条据此改写）。
5. **线路过滤进快照 key**：规则变了就换 key（原先刻意"不进"）。

## 理由

- **判据必须与客户端看到的一致**：同一套规则两处各写一遍迟早会分叉，所以实现只留一份，
  emby 层与聚合层都引用它 —— "聚合以为有用、客户端 0 个版本"这类矛盾才不会再出现。
- **补打要按客户端的口径凑数**：实测同一请求里"过滤前能用 2 条"，若按过滤前判据就到此为止；
  按过滤后判据则会继续补打并凑到 3 条能用的。也就是说，改判据不只是"少存一份没用的快照"，
  还**真的多找出了可播的版本**。
- **没用的结果不该被存**：存下来等于"在有效期内锁定一个 0 版本的结果"（实测客户端连问四次都是 0），
  而重算是有机会拿到有用结果的（那一趟里另外两个站失败，下一次未必失败）。
- **规则进 key 与"规则立刻生效"不冲突**：进 key 之后改规则同样是立刻生效，只是**第一次要重算**；
  不进 key 则可能命中一份"按旧规则判定为有用"的结果 —— 两者相权，选前者（见「后果」的代价）。

## 备选方案

- **只把"过滤后 0 条"排除出可存性、不动补打判据**：代价最小，但等于"不存快照、也不去找
  别的可用条目"—— 每次请求都重算，却仍然可能返回 0 条。收益只有一半，否决。
- **把过滤放到打分期（搜索到条目就按线路筛）**：打分期只有搜索结果的元信息，**看不到线路名**
  （线路名只在 `/detail` 响应里），做不到，否决。
- **不缓存"过滤后 0 条"，但把过滤规则挡掉的那几条线路也列给客户端**：违反规则本身的意图
  （规则就是"只列匹配的线路"），且会让规则形同虚设，否决。
- **保持 ADR-0020 原判据、只在 emby 层加一句"这次是规则滤掉的"日志**：现状本来就有这句日志，
  问题不是"看不出来"而是"锁死一个有效期"，否决。

## 后果

- **改过滤规则后第一次请求要重算**（那一趟 10~20 秒）；旧规则下的快照不会被主动删，按 TTL 自然淘汰。
- **规则写得太窄（谁都不匹配）时**：每个请求都会补打到上限（`maxItems + matchExtraK` 条，勾了
  「匹配到底」则打到名单完）才收手，且**不存快照** → 同一部片会被反复重算。信号是这行日志：
  `· agg 线路过滤 /…/：过滤前能用 X 条 → 过滤后能用 0 条`。
- `stats` 多两个字段：`usable`（过滤后可用条数，快照判据）、`usableBeforeFilter`（过滤前，诊断用）。
- 聚合层多一行日志（规则生效时）：
  `· agg 线路过滤 /…/：过滤前能用 X 条 → 过滤后能用 Y 条` —— "为什么还在补打""为什么一条都不列"
  都能一眼看出来。
- **客户端的版本列表行为不变**：过滤仍然只影响"列出来的版本"，不影响播放
  （`resolveStream` 按版本 Id 回查，不查这个列表）。
- ADR-0020 里「线路过滤不进 key」那一条**被本条目取代**，其余取舍（存半份、负结果不存、只到集 id）
  仍然有效。
