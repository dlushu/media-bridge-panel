# ADR-0020 详情快照：把"连问三遍"的那一步存下来

- 状态：已采纳（其中「线路过滤不进 key」这一条已被 [0025](0025-line-filter-in-usable-judgement.md) 取代）
- 相关：[agg/cache.js](../../server/modules/agg/cache.js) · [agg/api.js](../../server/modules/agg/api.js) · [emby/service.js](../../server/modules/emby/service.js) · [cachedb.js](../../server/core/cachedb.js) · [0011](0011-cache-split-by-consumer.md) · [0006](0006-redirect-for-playback.md) · [0008](0008-no-fabricated-data.md) · [0025](0025-line-filter-in-usable-judgement.md)

## 背景

客户端点一次播放，会连着问三遍**同一件事**：条目详情 → 播放信息① → 播放信息②。
而每次都要重跑「搜源 → 逐站取详情 → 定位到这一集」，实测 4~7 秒 —— 三次串行约 20 秒，
其中两遍是白重算的（参数完全相同）。

另有一处纯浪费：**「剧集详情」**。剧与季在客户端里是**容器**，按设计本来就不给版本列表，
但原先会先把整条源链跑完（5~6 秒）、算出线路与定位，**然后**才发现类型不可播、把结果全丢掉。

## 决定

1. **缓存聚合层的详情结果**（"这一集有哪些线路" + "定位到源里哪一条"）到
   `data/cache/detail.db` 的 `detail_cache`（由 `modules/agg/cache.js` 声明，复用 [0011](0011-cache-split-by-consumer.md) 的通用缓存设施）。
2. **剧集与季的详情在拿到元数据后按类型提前返回**，源那一趟不跑。
3. **同一 key 的并发请求共享同一趟源查询**（同一时刻两个人点开同一部片只打一次源）。
4. 覆盖范围与边界：
   - 缓存 key = 影视名 + 年份 + 季 + 集 + **规则指纹**（参与站点、源地址、分数线、最多留几条、补打设置、站点顺序、**线路过滤**）；
   - **只缓存到"集 id"为止**，播放地址不缓存；
   - **至少有一条"客户端能列出来的线路"才写**（判据 = `stats.usable > 0`：有线路、过了线路过滤、
     且定位到这一集 / 有播放项 —— 见下面「理由」与 [0025](0025-line-filter-in-usable-judgement.md)）、
     **负结果不写**；
   - 只有「按名字搜」那条路缓存，带 `源 + 站点 + vodId` 的快路径不缓存。

## 理由

- **把规则拼进 key，而不是写失效钩子**：改站点勾选 / 分数线 / 上限之后 key 自然不同，
  不可能读到按旧规则算出来的结论；也就不需要"设置变更后清缓存"这条容易漏改的链路。
- **线路过滤进 key**（原先写的是"不进"，已被 [0025](0025-line-filter-in-usable-judgement.md) 取代）：
  过滤现在参与"这条详情对客户端有没有用"的判据（过滤后一条都列不出来的不算有用），
  所以规则一改就必须换 key —— 否则会命中一份"按旧规则判定为有用"的结果。代价是改规则后第一次要重算。
- **只到"集 id"为止**：播放地址有时效（[0006](0006-redirect-for-playback.md) 定的是每次 302 现取），
  缓存它等于缓存一个会过期的地址。快照里的集 id 同样是时效 token，所以这张表是**分钟级**短缓存。
- **只不写负结果，有站失败照写**（判定收敛成"至少有一条客户端能列出来的线路"，见 [0025](0025-line-filter-in-usable-judgement.md)）：
  原先还要求"没有站失败、没有详情失败"，理由是"一次网络抖动被存住，之后整个有效期内的版本列表都会缺那几条线路"。
  实测下来这个严法**代价太大**：这一趟是 **10 秒级**的活（实测中位 10.8s），而 5 个启用站里只要有一个慢/抖一下，
  整份就不写 —— 于是客户端点一次播放连着问的三遍（条目详情 → 播放信息① → 播放信息②）**全部重算**，
  一次播放要等 20~30 秒；而写下来最坏也只是"缺某个源那几条线路"这一档损失。两害相权取其轻。
  为了让"缺的线路"不再无声无息，**写快照那行日志会点名**这次是哪个源没搜到 / 有几条详情没取到。
  判据里仍保留"分不清就不缓存"的那半：没命中、或全失败（返回值上分不清）一律不写（延续 [0008](0008-no-fabricated-data.md)）。
- **快路径不缓存**：`源 + 站点 + vodId` 那条路是拉流时取**新鲜**集 id 用的；缓存它会拿到过期 id。
- **提前判类型不改变响应**：容器类型本来就不展开版本列表（`sources` 为空时，条目级
  `Container`/`MediaStreams`/`Path` 那几个字段本来也不会被填），所以这是纯粹少跑一趟。

## 备选方案

- **把集 id 编进 `MediaSourceId`**：早前已否决 —— 夸克类集 id 约 460 字符，编进去会让客户端请求的
  URL 涨到 700 字符上下，一旦被中间环节截断就是"点了播不了"。
- **只做进程内内存缓存**：改动更小，但重启即丢、面板上看不到用量、也不能被"清空缓存"清掉。
- **缓存上游那两次调用（搜索 / 单站详情）**：key 天然正确、web 的聚合页也能受益，但单个剧的
  详情响应体不小（几十到几百 KB），要单独定字节上限；且会让 web 的"现在源里有什么"跟着变陈旧。
  先做结果级，将来需要下沉再评估。
- **让"播放信息②"只回客户端指定的那一个站**：会把①已经发给客户端的其余线路**悄悄丢掉** ——
  与 [0008](0008-no-fabricated-data.md) 的取向冲突，不做（对照实现里这一步也是回完整清单）。

## 后果

- 面板侧从约 18 秒降到 **约 0.5 秒**（第一次仍要打一趟源，那趟实测 4~7 秒）；同一部片在有效期内
  重复点开为**几十毫秒**。剧集详情 5~6 秒 → 0.3 秒左右。
- 缓存多一张表：面板「缓存设置」多一行用量、多两个设置项（分钟数 / 长期有效），
  「清空缓存」一并清它，字节上限写死在代码里（不暴露）。
- 「长期有效」只对**之后写入**的快照生效：已经存下的那条仍按它写入时算好的时间过期。
- 快照命中时，版本列表里的集 id 可能是旧的；它只出现在诊断字段里，**不影响播放**
  （拉流按"线路 + 这一集"回查，取的是新鲜 id）。
- 副作用之一：命中快照时聚合层不会再打"打分摘要"那行日志，改打一行"走快照"；
  判断有没有真的打源站，看这行即可。
- ⚠️ **可能存下"不完整"的快照**（2026-09-23 起）：某个源当时没搜到 / 有详情没取到时也照写，
  于是那个有效期内点开这部片都会缺它的线路。**代价知情接受**，靠日志点名来兜底：
  `✔ agg 详情已存快照（N 站；⚠️ 但不完整：…）`。
- ⚠️ **线路过滤写得太窄时会反复重算**（[0025](0025-line-filter-in-usable-judgement.md)）：
  过滤后一条都列不出来的结果**不存快照**，于是同一部片每次点开都要重走源站那一趟（10~20 秒），
  而且会补打到上限才收手。信号是聚合层那行
  `· agg 线路过滤 /…/：过滤前能用 X 条 → 过滤后能用 0 条`。
