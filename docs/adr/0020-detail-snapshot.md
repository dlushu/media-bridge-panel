# ADR-0020 详情快照：把"连问三遍"的那一步存下来

- 状态：已采纳
- 相关：[agg/cache.js](../../server/modules/agg/cache.js) · [agg/api.js](../../server/modules/agg/api.js) · [emby/service.js](../../server/modules/emby/service.js) · [cachedb.js](../../server/core/cachedb.js) · [0011](0011-cache-split-by-consumer.md) · [0006](0006-redirect-for-playback.md) · [0008](0008-no-fabricated-data.md)

## 背景

客户端点一次播放，会连着问三遍**同一件事**：条目详情 → 播放信息① → 播放信息②。
而每次都要重跑「搜源 → 逐站取详情 → 定位到这一集」，实测 4~7 秒 —— 三次串行约 20 秒，
其中两遍是白重算的（参数完全相同）。

另有一处纯浪费：**「剧集详情」**。剧与季在客户端里是**容器**，按设计本来就不给版本列表，
但原先会先把整条源链跑完（5~6 秒）、算出线路与定位，**然后**才发现类型不可播、把结果全丢掉。

## 决定

1. **缓存聚合层的详情结果**（"这一集有哪些线路" + "定位到源里哪一条"）到
   `data/cache/detail.db` 的 `detail_cache`（由 `modules/agg/cache.js` 声明，复用 [0011](0011-cache-split-by-consumer.md) 的通用缓存设施）。
2. **剧集与季的详情在拿到元数据后按类型提前返回**，源那一趟不跑。
3. **同一 key 的并发请求共享同一趟源查询**（同一时刻两个人点开同一部片只打一次源）。
4. 覆盖范围与边界：
   - 缓存 key = 影视名 + 年份 + 季 + 集 + **规则指纹**（参与站点、源地址、分数线、最多留几条、补打设置、站点顺序）；
   - **只缓存到"集 id"为止**，播放地址不缓存；
   - **有站失败不写**、**负结果不写**；
   - 只有「按名字搜」那条路缓存，带 `源 + 站点 + vodId` 的快路径不缓存。

## 理由

- **把规则拼进 key，而不是写失效钩子**：改站点勾选 / 分数线 / 上限之后 key 自然不同，
  不可能读到按旧规则算出来的结论；也就不需要"设置变更后清缓存"这条容易漏改的链路。
- **线路过滤不进 key**：过滤是在 emby 层拿到结果之后做的，聚合结果本身不带过滤 ——
  所以改过滤规则**立刻生效**，与快照无关。
- **只到"集 id"为止**：播放地址有时效（[0006](0006-redirect-for-playback.md) 定的是每次 302 现取），
  缓存它等于缓存一个会过期的地址。快照里的集 id 同样是时效 token，所以这张表是**分钟级**短缓存。
- **不缓存失败与负结果**：一次网络抖动被存住，之后整个有效期内的版本列表都会缺那几条线路，
  而日志上跟"源里确实没有"长得一样 —— 分不清就不缓存，每次如实去问（延续 [0008](0008-no-fabricated-data.md)）。
- **快路径不缓存**：`源 + 站点 + vodId` 那条路是拉流时取**新鲜**集 id 用的；缓存它会拿到过期 id。
- **提前判类型不改变响应**：容器类型本来就不展开版本列表（`sources` 为空时，条目级
  `Container`/`MediaStreams`/`Path` 那几个字段本来也不会被填），所以这是纯粹少跑一趟。

## 备选方案

- **把集 id 编进 `MediaSourceId`**：早前已否决 —— 夸克类集 id 约 460 字符，编进去会让客户端请求的
  URL 涨到 700 字符上下，一旦被中间环节截断就是"点了播不了"。
- **只做进程内内存缓存**：改动更小，但重启即丢、面板上看不到用量、也不能被"清空缓存"清掉。
- **缓存上游那两次调用（搜索 / 单站详情）**：key 天然正确、web 的聚合页也能受益，但单个剧的
  详情响应体不小（几十到几百 KB），要单独定字节上限；且会让 web 的"现在源里有什么"跟着变陈旧。
  先做结果级，将来需要下沉再评估。
- **让"播放信息②"只回客户端指定的那一个站**：会把①已经发给客户端的其余线路**悄悄丢掉** ——
  与 [0008](0008-no-fabricated-data.md) 的取向冲突，不做（对照实现里这一步也是回完整清单）。

## 后果

- 面板侧从约 18 秒降到 **约 0.5 秒**（第一次仍要打一趟源，那趟实测 4~7 秒）；同一部片在有效期内
  重复点开为**几十毫秒**。剧集详情 5~6 秒 → 0.3 秒左右。
- 缓存多一张表：面板「缓存设置」多一行用量、多两个设置项（分钟数 / 长期有效），
  「清空缓存」一并清它，字节上限写死在代码里（不暴露）。
- 「长期有效」只对**之后写入**的快照生效：已经存下的那条仍按它写入时算好的时间过期。
- 快照命中时，版本列表里的集 id 可能是旧的；它只出现在诊断字段里，**不影响播放**
  （拉流按"线路 + 这一集"回查，取的是新鲜 id）。
- 副作用之一：命中快照时聚合层不会再打"打分摘要"那行日志，改打一行"走快照"；
  判断有没有真的打源站，看这行即可。
