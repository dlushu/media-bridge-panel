# ADR-0001 模块分层与依赖方向

- 状态：已采纳
- 相关：[ARCHITECTURE.md](../../ARCHITECTURE.md) · [0002](0002-in-process-emby-to-agg.md)

## 背景

面板同时承担四件事：托管数据源、聚合搜索、对外提供 Emby 兼容接口、管理自身设置。
这些能力耦合在一个进程里，如果没有约束，很容易出现互相 `require` 形成的依赖环
（例如 emby 层直接读聚合层的配置），使上游实现无法替换、也无法单独理解某一层。

## 决定

分四层，依赖方向单向：

```
source（数据源层） ← agg（聚合层） ← emby（消费层）
        ▲
   panel（宿主层）：不参与数据链
```

- 跨模块数据流一律走「地址 + HTTP」，模块之间不互相 `require` 业务逻辑。
- 每个模块在自己的设置中记录所消费的上游地址 `upstream.<模块id>`；该地址允许指向外部实现
  （例如把聚合层的源指向另一台机器上的源）。
- 模块自己声明对外前缀 `apiPrefix` 与上游 `upstream`，由 `core/registry.js` 汇总。
- 唯一的向下 `require`：解析上游地址时读本地进程状态（本地运行中源的端口），
  即 `agg/routes.js → ../source/service.resolve()`。

## 理由

- 上游可替换：源的地址可以指向外部实现，因此不能假设"上游一定在同进程"。
- 边界清晰：每层只看得到上游的地址与协议，不依赖上游的内部结构。

## 备选方案

- **同进程互相 `require` 业务逻辑**：实现最短，但无法替换上游，且任何一层改动都可能牵动其它层。
- **拆成多个进程**：边界最硬，但部署复杂度与资源占用显著上升，对路由器这类设备不划算。

## 后果

- 新增模块必须声明 `apiPrefix` 与 `upstream`；模块设置会自动获得
  `data/settings/<id>.json` 与 `/api/modules/<id>/settings`，无需改 `core`。
- 唯一的例外是 emby 层对聚合层的调用，后来改为进程内直调，见 [ADR-0002](0002-in-process-emby-to-agg.md)。
