# ADR-0026 聚合超时：搜索与取详情分开，时间单位统一为秒

- 状态：已采纳
- 相关：[agg/settings.js](../../server/modules/agg/settings.js) · [agg/service.js](../../server/modules/agg/service.js) · [agg/api.js](../../server/modules/agg/api.js) · [agg/routes.js](../../server/modules/agg/routes.js) · [0020](0020-detail-snapshot.md) · [0025](0025-line-filter-in-usable-judgement.md)

## 背景

聚合链路上原来只有一个超时旋钮 `agg.timeoutMs`（毫秒，默认 5000），**搜索、播放、首次 `/init`
与取详情共用**它。两个问题：

- **详情被搜索的超时整除**：取详情是"拉一部片的全部线路与选集"——剧集的目录动辄几十上百集，
  响应体大、上游拼装慢，与搜索（只回一页列表）不是一个量级。实测同一条 `/detail` 2~10 秒，
  共用 5 秒会把"目录里内容多的那种"一律记成超时，表现为**大量"定位不到 / 取不到详情"**，
  而站其实是好的 —— 量到的是设置，不是站。
- **毫秒为单位不合用**：这个旋钮是"偶尔调一次"的参数，页面上写 `5000` 要数零；
  上下文（文档、聊天、排查记录）里也总有人把它当成秒。

## 决定

1. **时间单位统一为秒**：`agg.timeoutSec`（搜索 / 播放 / 首次 `/init`，默认 **5**，范围 1~60）。
   设置文件、页面、文档一律用秒；毫秒只在服务端内部（`request()` 的 `timeout`）出现。
2. **取详情独立成一项**：`agg.detailTimeoutSec`（默认 **10**，范围 1~120）——
   只作用于 `POST /detail`，理由是上面的"剧集目录大"。
3. **旧值不丢**：启动时一次性搬迁 `timeoutMs → timeoutSec`（四舍五入、夹到 1~60），
   随后删掉旧键。**不写兼容分支**：搬迁只在路由注册时跑一次，干净了就是空操作。
4. **详情超时进详情快照的 key**（`api.detailCacheKey`）：它决定"这一次哪几条线路取得到"
   （超时的站那条就没了），与线路过滤同理 —— 改了规则就该重算，而不是命中一份按旧超时算出来的结论。
5. **前端给一张"运行时流程与耗时"说明卡**：把聚合参数、打分设置、线路过滤翻译成
   "跑一次会发生什么、大概等多久"（五步 + 最坏 / 正常量级），**数字跟着输入框实时算**、
   不必保存。同时给出最坏与正常两个量级。

## 理由

- **两个旋钮对应两条不同的链路**，共用一个必然要么压坏详情、要么放过坏搜索：
  搜索要的是"快站优先、慢站别拖累整轮"，详情要的是"大目录也能取回来"。
- **秒是这一层唯一合理的单位**：取值区间只有 1~120，秒的分辨率足够（毫秒在这个量级上是噪声），
  而"写 10 就是 10 秒"省掉一整类误读。
- **搬迁必须做**：用户调过的 `12000` 如果被静默退回默认 5 秒，是**两倍多**的行为变化，
  且症状（突然大量超时）很难联想到"单位改了"。
- **进 key 与"改规则立刻生效"不冲突**：进 key 之后改超时同样是立刻生效，只是第一次要重算；
  不进 key 则可能命中一份"按旧超时丢掉了几条线路"的快照 —— 两者相权，选前者（见「后果」的代价）。
- **运行时说明要"实时 + 双量级"**：这些旋钮的后果（最坏等多久）本来只存在于代码里；
  只报上限会把人吓到，只报"一般 2 秒"又与实测（确实有 15 秒级的站）不符，所以两个都给，
  并标明哪个是上限。

## 备选方案

- **详情仍复用 `timeoutSec`、只是默认值调大**：等于让搜索也陪着等 10 秒 —— 一轮搜索的最坏耗时
  直接翻倍（并发下按最慢那一批算），否决。
- **把详情超时做成"按站点"或"按影视类型（电影 / 剧集）"**：站点清单里没有"目录多大"这个信息，
  按类型则要求调用方先知道类型（搜索阶段还不知道），做不到，否决。
- **保留毫秒、只在页面上显示秒**：存的是毫秒、显示是秒，改一次设置就可能被四舍五入掉
  （`5000` ↔ `5` 没问题，但用户填 `5500` 会显示成 `5.5`），引入一类无意义的精度问题，否决。
- **不搬旧值、直接忽略 `timeoutMs`**：实现最省事，但会让调过的值静默失效（理由见上），否决。
- **把详情超时也进"打分/补打"的判据**（用它决定"这条算不算超时失败"）：现状已经如此
  （超时即 `ok:false`，不算"能用"），不需要额外机制。

## 后果

- **改详情超时后第一次请求要重算**（那一趟 10~20 秒）；旧超时下的快照不会被主动删，按 TTL 自然淘汰。
- 详情更宽（10 秒）意味着**一轮详情最坏更久**：阶段一并发打 ≈ 等最慢那一发（≤10 秒），
  补打每批 ≤10 秒。这是有意的取舍 —— 用**上限变长**换"大目录也能取回"。
- 设置键 `timeoutMs` 消失：直接读 `agg.json` 的脚本 / 教程要改成 `timeoutSec`；
  盘上的 `timeoutMs` 会被搬迁后删除（日志会打一行 `单站超时 12000ms → 12s`）。
- `/api/agg/sites` 的 `agg` 与兼容层 `/api/settings` 仍**给毫秒**（`timeoutMs` /
  `detailTimeoutMs`）：前端拿它与测速结果比（"比它慢的站在聚合里必被判超时"），
  那一处比较的就是毫秒，不跟着换成秒。
- 请求级覆盖仍是毫秒：`POST /api/agg/search` 的 `timeoutMs`、`POST /api/agg/detail` 的
  `timeoutMs` / `detailTimeoutMs` —— 它们是"这一次"的精细控制，不是设置。
- 设置页多一个输入框、多一张说明卡；站点表那一列「延迟」的标红判据不变（仍是搜索超时）。
