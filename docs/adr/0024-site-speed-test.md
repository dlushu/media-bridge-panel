# ADR-0024 站点测速：服务端任务、打 `/search`、随机片名

- 状态：已采纳
- 相关：[site-test.js](../../server/modules/agg/site-test.js) · [site-stats.js](../../server/modules/agg/site-stats.js) · [agg/api.js](../../server/modules/agg/api.js) · [0016](0016-source-auto-update-default-off.md) · [0008](0008-no-fabricated-data.md)

## 背景

「站点与参数」页需要一列"这站现在快不快 / 还活不活"的指标，用来决定勾选哪些站参与聚合。
原先有两处数据来源，各有毛病：

- **顺手记账**：真实搜索 / 取详情时把耗时记一笔（取**中位数**，每站留最近 20 个样本 + 成败计数）。
  零成本，但它记录的是"过去那些次"的混合值 —— 站点刚刚变慢（或刚恢复）在界面上看不出来。
- **前端逐站体检**：浏览器按 3 并发逐站调单站端点。关掉页面就断，而且**"每 6 小时自动测一轮"
  与"某个源起来后立刻测一轮"这两件事，它根本做不了**。

在改为服务端任务之前，先把"测什么"量清楚（路由器上两个源、52 个站 + 6 个站的重复测量）：

| 观测 | 结果 |
|---|---|
| 源侧搜索缓存 | **有**：`SEARCH_CACHE_MINUTES` 默认 **3 分钟**、内存 Map 上限 500 条、键取自搜索词，命中会打 `[cache] Using search cache for "…"`。同一词连打会明显变快（实测 huban 212 → 93ms） |
| `/search` 的 404 | **两种来源、长得一样、含义不同**：站里没有这个词（响应体是上游 axios 形状 `{"statusCode":404,"code":"ERR_BAD_REQUEST",…}`）与源里这个站没实现该端点（`{"message":"Route POST:/spider/zhuiju/3/search not found"}`） |
| 冷 / 热差 | `/home` 约 2 倍（1893 → 793ms）；`/search` 2~25 倍（视站点缓存策略而定） |
| `/home` 能否当速度 | **不能**：它返回首页分类树（huban/duoduo 各 62KB、208 个分类；盘搜类站是空壳 10ms），与搜索耗时背离（duoduo 首页 2.0s / 搜索 0.4s、huban 1.4s / 0.1s）；52 个站里 7 个是空壳（10ms 的"最快站"） |

## 决定

1. 测速是**服务端后台任务**（`agg/site-test.js`）：并发 3、**全部站点**（只测已勾选的会让没勾的站
   永远没有数据，而这一列正是用来决定要不要勾它）、**跑完才排下一轮**。触发有三条：
   ① 每 `speedTestHours` 小时（默认 **6**）自动一轮，`speedTestAuto` **默认开**、可关；
   保存设置时**只有测速这两项真的变了才重排**（勾选站点、改线路过滤这类保存不会把下一轮往后推）；
   ② 手动（`POST /api/agg/site-test/start`，可带 `keys` 只测一批）；
   ③ **某个源起来 / 重启后自动测它的站点**（source 层只广播 `runner.onReady(id)`，
   `server.js` 接到聚合层 —— source 是最底层，不反向依赖 agg）。
2. 每站打**一发 `POST {api}/search`**，关键词从常见影视名数组里**随机取**；
   **非 200 就换一个词再测一发**，**两发都非 200 才算真失败**。
3. 超时**固定 15 秒**（`SPEED_TEST_TIMEOUT_MS`），**不读** `agg.timeoutSec`（也不读取详情那一项）。
4. 结果**每站每类只留最近一次**（单槽覆盖；删除样本数组与次数累计），TTL 30 天；
   「站点与参数」页显示为一列「延迟」。
5. 统计分两组槽：`speed.search`（测速口径）与 `call.search` / `call.detail`（顺手记账的业务口径）。
   **"聚合搜索要不要跳过这个站"只看测速那一槽**（`speed.search` 失败 = 跳过，成功即恢复），
   **没有时间窗口** —— 时效由测速周期决定（默认 6 小时一轮；也可以用行内那个「测速」按钮立刻复测）。
   行内那一个按钮 = **单点测速**（只测一个站，同步返回、结果直接写进同一槽）。
6. 详情不再由测速产生：详情耗时只在**真实取详情**时记账，没人点开过的站如实为空。

## 理由

- **只有 `/search` 是聚合真正走的链路**，它的数字才对得上"用户要等多久"。`/home` 虽然普遍可用
  （52 个站里 44 个 200）、也没有"无结果"这种语义，但它复述的是首页分类，实测与搜索耗时背离，
  当"延迟"列会误导挑站。
- **随机片名 + 失败换词**：把"这站恰好没有这个片名"从变量里去掉。固定一个词时，
  站里没这个词会回 404 或空列表（实测 duoduo / huban），等于给每个站预设了不同条件。
- **固定 15 秒**：业务超时默认 5 秒，是给播放链路用的；拿它去测速会把慢站一律记成超时，
  量到的是设置而不是站。
- **单槽覆盖**：这一列要回答的是"现在怎么样"。中位数代表的是过去，而且界面会挂上
  "（20 次）"这类与决策无关的信息；既然已经每 6 小时刷一轮，历史没有额外价值。
- **分槽**：两处要答的问题不同 —— 表格那一列答的是"这站现在能不能搜出东西"（测速口径，
  404 / 5xx / 超时 / 两发都失败 = 失败），单元格 `title` 里答的是"真实业务里它上次花了多久"
  （业务口径，404 = 无结果、不算失败）。共用一槽两者会互相覆盖。
- **跳过判据用测速口径、且不带时间窗口**：这样"表里标红的站"与"聚合里被跳过的站"是**同一个集合**
  —— 不会出现"看着是红的、搜索却还在打它"，也不会出现"站已经恢复了、却因为窗口没到还在被跳"。
  恢复时机完全由测速（定时或手动单点）决定，比一个独立的十分钟计时器好解释。

## 备选方案

- **用 `/home` 当探针**（无关键词、无假 404、普遍可用）：与搜索耗时背离，且有大批空壳站，
  否决。
- **用固定关键词测 `/search`**：源侧 3 分钟缓存 + 各站对该词的命中量不同 → 数字既不可比也不稳，
  否决。
- **沿用 `agg.timeoutSec`**：默认 5 秒会把慢站一律记成超时，否决。
- **保留样本数组取中位数**：与"定期刷新"的口径冲突，且实现更重，否决。
- **测速留在前端**：关页面即断，做不到定时与"源起来后触发"，否决。
- **把测速并进播放链路**（用真实业务耗时当指标）：只在站点被用过时才有值，
  且不同站点被使用的频率差异极大，无法构成可比的横截面，否决。

## 后果

- **默认开启意味着面板会持续向上游发搜索请求**：每站每轮 1~2 发 `/search`（外加首次 `/init`），
  每 6 小时一轮。这是它必须"跑完才排下一轮"的原因；关掉它是「聚合参数」页的一个开关。
- **测速结果是"失败站跳过"的唯一判据**：`404` 也算失败（那正是"这站搜不出东西"），所以
  探测词没命中的站会被跳过 —— 随机片名 + 失败换词已经把这种情况压到很低，而且行内「测速」
  按钮随时可以复测、下一轮也会自动重测。
- 详情耗时不再由测速伪造：没被点开过的站，详情一栏为空（如实留空，见 [ADR-0008](0008-no-fabricated-data.md)）。
- `agg.initFirst` 开关删除（init 恒开）：测速每轮都走同一个 `ensureInit()`，一轮测速跑完
  等于全站都 init 过，这个旋钮没有存在意义；源重启换端口时缓存键变化，业务侧仍会兜底 init。
- `sitestat.db` 仍是**可丢弃**数据（「面板设置 → 缓存设置 → 清空缓存」会一并清掉）。
- 界面不再有「全选可搜索」按钮：源的 `searchable` 常漏报，批量勾选会漏掉能用的站；
  挑站改为看「延迟」列（并可三态排序）。
