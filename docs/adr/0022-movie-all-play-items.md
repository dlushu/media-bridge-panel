# ADR-0022 电影取法：每条线路列出全部播放项（与剧集的按集号定位并存）

- 状态：已采纳
- 相关：[0003](0003-local-title-scoring.md)（挑片判据：本地打分，不猜） ·
  [0006](0006-redirect-for-playback.md)（播放一律 302） ·
  [0019](0019-self-update-from-release.md)（应用按 Release 安装，与本条无关但同属"版本"语义）
- 实现：`server/modules/agg/service.js`（`fetchDetail` 的取法分支、`detailUsable`）·
  `server/modules/emby/service.js`（`wantLocator` / `catpawSourceId` / `resolveStream` / 拼版本列表）

## 背景

站源协议里电影与剧集**同构**：一条线路 + 若干播放项（`vod_play_url` 里 `#` 分隔的那些），
播放时只要「线路 + 选集ID」（见猫爪源接口协议的 `/detail` 与 `/play`）。

- **剧集**的每个播放项 = 一集，名字里通常带集号（`第03集` / `S01E03` / `211 4K.mp4`），
  所以"按集号定位这一集"成立。
- **电影**的播放项**没有集号** —— 名字里只有体积、年份、分辨率、编码。实测该场景：
  `[5.0GB]2026.1080p.英语中字.mp4`、`[4.4GB]2026.HC1080P.X265.AC3.English.CHS-ENG.ZZYS.mkv`、
  `[1.6GB]清晰版.2026.HC1080P.X265…mp4`（同一部片的四个压制版本）。

早期做法是**让电影借剧集的定位**：`wantLocator()` 对电影传 `season: 1, episode: 1`，
假设聚合层的「第 1 季按**选集序号**」规则会取到第一条播放项，于是 `Id` / `Path` / 拉流整条链路都不用改。
但这个假设已经失效 —— `locateEpisode()` 的第 ③ 步后来改成"按数字匹配"
（原注释写明"**取代**原来的「按选集序号（该行第 N 个）」兜底"），而电影文件名里的数字全被规格规则排除
（`2026` 后面紧跟 `.1080` 按小数/规格跳过；`1080p` / `X265` / `AC3` / `.mp4` 因数字紧邻字母被排除）。

后果实测（TMDB 首页 20 部电影，按客户端对电影的坐标 `S1E1` 逐部走聚合详情）：

| 结果 | 部数 |
|---|---|
| 客户端版本列表 **0 条**，而源里有 4~20 条线路（卡在"定位"这一步） | **17** |
| 客户端版本列表 0 条，源里也没取到详情/没命中（另一类问题） | 2 |
| 有版本（文件名里恰好有个能被认成 `1` 的数字） | 1 |

也就是说：**电影能不能看，取决于文件名里有没有一个能被认成集号的数字**，且失败时客户端只看到"没有版本"，
没有任何提示。

## 决定

**电影与剧集用两套取法，显式区分，不再互相借。**

- 聚合层 `fetchDetail` 收一个显式取法 `pick`：
  - `pick: 'items'`（**电影**）—— 每条线路的**每个播放项**都算一个可播目标（`line.items[]`），
    不按集号匹配；`line.target` 仍保留 = 第 1 项（诊断字段与既有消费方不用改）。
  - 缺省（**剧集**）—— 原样：按季集号定位，产出 `line.target`。
- emby 层 `wantLocator()`：电影 → `{ pick: 'items' }`；集 → `{ season, episode }`。
- **版本 = 线路 × 播放项**（电影）：同一部片的多个压制版本各自成为一个版本，标题位挂源标的规格
  （`5.0GB 1080p`；规格重复或读不出时补 `· 第 N 项`，保证互不相同 —— 标题撞名的后果是客户端里几条版本
  长得一模一样），由客户端自己挑。
- **版本 Id 加一个项序号**：载荷 `{s,t,f,v,i?}`，`i = 0` 时**不写进载荷**。于是"第 1 项"的 Id 与改动前
  逐字相同，客户端缓存着的旧 Id 天然等价于第 1 项 —— 不需要单独的老 Id 兼容分支。
- 拉流（`resolveStream`）按 `i` 取项，与拼版本列表**同一口径**（否则"版本列出来了、点了 404"）；
  「列表备忘」的 key 也带 `i`（否则同线路的多个版本互相覆盖，结果永远播第 1 项）。
- **剧集那条链不动**：定位、Id 形状、播放路径一字未改。

## 理由

| 做法 | 得到什么 | 付出什么 |
|---|---|---|
| **两套取法**（本决定） | 电影能列出全部压制版本、点开即可播；剧集零影响 | 多一个契约参数 `pick` 与 Id 里的 `i` |
| 继续借 `S1E1`（原状） | 零改动 | 实测 19/20 部电影拿不到版本 |

与"不猜"的口径一致：电影的播放项**没有集号**，"把每条线路的播放项列出来"是符合协议语义的确定取法
（`/play` 本来就只吃「线路 + 选集ID」），**不是猜**；反而是"借 `S1E1` 指望取到第一条"属于猜。

## 备选方案

- **电影只取第 1 项**：改动更小，但"第 1 项"同样是猜（可能是预告或低码版本），也把选择权拿掉了。已否决。
- **把选集ID 编进版本 Id**（"版本 Id 直接对应集 id"）：最贴协议、播放时不必回查，但选集ID 实测
  592~720 字符（客户端拉流 URL 总长约 1000 字符），且**选集ID 会过期** —— `agg/api.js` 的快路径注释写明
  "缓存它会拿到过期的集 ID，所以那条路一律不缓存"，而客户端持有 Id 的时长不可控。**尤其伤害剧集**
  （看剧最容易跨越很长的时间窗），已否决。
- **按规格挑"最好"的那一项**：属于猜，且"最好"没有依据（体积大不等于合适）。已否决。
- **剧集也改成列出全部播放项**：剧集一条线路下有 200+ 集，会把每一集都列成一个版本 —— 语义完全错。已否决。

## 后果

- **电影版本数 = 线路数 × 播放项数**（实测「生化危机：爆发夜」经 `play.filter` 的 `夸克` 过滤后
  **10 个版本**、不过滤 26 个），客户端版本列表会明显变长。先如实全列，觉得乱再加"每条线路最多 N 项"。
- 若某条线路把「预告」与正片并列，预告也会成为一个可播版本 —— 不猜、不挑，由客户端自己选。
- 诊断字段与日志口径跟着改：电影写「N 个版本（M 条线路 × 播放项）」「条目有播放项」，
  不再把"没有播放项"说成"没定位到"。
- **老 Id（不带 `i`）等价于第 1 项**：面板升级/回退期间客户端手里旧的 Id 仍能播，不会出现"点了没反应"。
- `detailUsable`（接续补打"有没有拿到一条能用的"的判据）跟着取法走：电影看**有没有播放项**，
  剧集看**有没有定位到这一集** —— 否则会把"整条线路一个可播项都没有"的条目算成可用。
