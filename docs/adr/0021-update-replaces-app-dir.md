# ADR-0021 更新即完整替换：只保留当前版本

- 状态：已采纳
- 相关：[0019](0019-self-update-from-release.md)（自身更新的目录布局、校验口径与重启协议，本条目只修订其中
  "旧版本一律保留"这一取向） · [update.js](../../server/modules/panel/update.js)（安装、清理与启动钩子） ·
  容器引导脚本 `docker/entrypoint.js`（首次安装与监督；由维护者维护，与容器定义一起放在版本库之外）

## 背景

按 [0019](0019-self-update-from-release.md) 的布局，每次更新都会在数据卷里**新增**一个 `app/<版本>/`，
旧版本一律保留，初衷是"本机随时能退回去"。

实际部署里这一取向的收益很小，成本却持续存在：

- 每个版本的应用代码约 900KB 上下。保留多份省不出可观空间，留下的是长期并存的目录与持续占用的盘。
- **保留旧目录并不构成回退能力**：面板界面从来没有回退入口，而唯一的手动回退路径是把
  `APP_VERSION` 指向旧版本再重启容器 —— 引导脚本发现该版本不在磁盘上会按 Release 重新下载。
  也就是说，删掉旧目录只是把回退从"本地现成"变成"联网再取一次"，并没有关闭这条路。
- 多版本并存让"现在跑的是哪一版"出现多个来源（`package.json`、`current.json`、磁盘目录清单、
  面板卡片上的"已安装 / 上一版"），每一处都可能与事实不一致。实测中就出现过机器上跑着某一版、
  而该版本的 Release 已被删除的情形 —— 卡片上"已安装 / 上一版"与实际能否回退并不对应。
- 发布流程是"先在机器上验证通过才推标签"，"装上新版本发现不能用"这一情形已由发布前验证覆盖，
  不需要再靠本地多留一份兜底。

## 决定

**更新即完整替换：`app/` 下恒只有当前运行的那一份。**

- **安装流程不变**：下载 → 校验 sha256 → 解到 `app/.staging-<版本>-<pid>/` → 校验必需文件 →
  原子改名成 `app/<版本>/` → 写 `current.json` → 写 `.restart` → 进程退出、由监督者拉起新版本。
  **安装阶段不删任何东西** —— 新版本还没跑起来时删旧版本，等于先把唯一的退路扔掉。
- **清理由新版本自己在启动成功后执行**（`server.js` 的监听回调里调 `update.pruneOnBoot()`），
  延迟十几秒再动手：
  - 清理逻辑只存在于新版本里，旧版本无需任何配合，因此第一次更新即可把历史版本收干净；
  - **每次启动都跑** ⇒ "只剩当前版本"在任何时刻都成立，不依赖"恰好发生过一次更新"；
  - 延迟窗口内新版本若立刻出问题，旧目录还在（本地唯一的退路）。
- **白名单（绝不删）**：正在运行的版本、`current.json` 记的版本、`APP_VERSION` 指定的版本。
  最后一条是必需的 —— 删掉它会让引导脚本每次启动都重新下载，网络不通时直接起不来。
- **只删"版本目录"与 `.staging-*` 暂存目录**：`current.json` 与 `.restart` 同样住在 `app/` 下，
  它们是监督者的协议文件，因此**绝不清空整个 `app/`**。
- **只在受管运行方式下执行**（`MB_SUPERVISED=1` 且代码位于 `app/` 之下）：直接跑源码时数据目录里的
  `app/` 不该被动。
- 前端不再展示"上一版"，卡片与确认框都改为"更新即完整替换"的措辞。

## 理由

| 做法 | 得到什么 | 付出什么 |
|---|---|---|
| **完整替换**（本决定） | 磁盘恒只有一份代码；"跑的是哪一版"只有一个来源；更新语义简单 | 本机无旧版本，回退需要重新下载 |
| 保留全部历史版本（[0019](0019-self-update-from-release.md) 原取向） | 回退时不必联网 | 多份代码与多个版本来源长期并存，"已安装 / 上一版"与实际能力不符 |

决定性的判断是上一条背景：**保留旧目录并不真的提供回退能力**。面板没有回退入口，而唯一的手动路径
（`APP_VERSION` + 重启容器）本来就会在目录缺失时重新下载，所以清理旧目录的代价只是"回退时联网再取一次"。

## 备选方案

- **保留最近 N 个版本**：比全留少占一些盘，但"N 取多少"没有依据，且多版本并存的语义成本一分不减。
- **原地覆盖同一目录**：删得最彻底，但**不可行** —— 静态文件是每个请求从磁盘读的
  （`core/http.js` 的 `serveStatic`），解包过程中与完成之后，运行中的进程会读到新旧混合的内容，
  表现为"新前端 + 旧后端"，甚至读到半个文件。
- **由监督者（引导脚本）清理**：时机更早也更权威，但引导脚本在镜像里，改动它意味着重推镜像并重建容器，
  而收益与"新版本启动后自己清"相同。
- **保持现状并补一个回退按钮**：需要为"本地目录回退"补一套界面与状态机；与"验证通过才发版"的发布方式
  相比，收益不足。

## 后果

- **回退路径**：`APP_VERSION=<旧版本>` + 重启容器 → 引导脚本发现目录缺失 → 按 Release 重新下载。
  由此得到一条操作约束：**删除某个 Release（标签与发布）后，运行该版本的机器再也装不回那一版**，
  删之前需确认没有机器在跑它。
- 启动后十几秒内，磁盘上可能短暂存在两份代码（正在跑的新版本 + 待清理的旧版本），属正常现象。
- 清理失败（权限、只读盘、文件被占用）只记一行日志，不影响运行；下次启动会再试一次。
- 用 `APP_VERSION` 固定某个版本的部署方式，在该版本不在磁盘上时会先下载一次再运行。
- `app/` 不再承担"版本档案"的作用；需要留档时应另外保存 Release 资产，而不是指望机器上的旧目录。
